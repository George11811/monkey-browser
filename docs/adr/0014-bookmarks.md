# ADR-0014：书签

- 日期：2026-10-13
- 状态：已实现（0.16.0）
- 相关文档：ADR-0008（会话恢复）、ADR-0012（`GM_openInTab`）

## 需求与定位

会话恢复（ADR-0008）**只恢复「上次开着的标签页」**，解决不了「这个页面我以后还会再看」。
书签补的就是这一块：用户主动标记的、跨会话长期保留的地址集合。

## D1：为什么用文件而不是 `PersistentStateComponent`

工程里两种做法都有先例（会话恢复用平台 `@State`，脚本库用文件）。书签选了**文件**，理由：

- **用户可直接编辑/备份**。书签是用户自己的数据，纯文本比 XML 更友好。
- **可脱离 IDE 单测**。[BookmarkStore] 不依赖任何 IDE API，用临时目录就能覆盖增删/去重/脏数据。
  （与会话恢复不同：那个天然绑定 Project，没法脱离平台。）

路径：`<config>/rider-monkey/bookmarks.txt`，与脚本库、GM 存储同处一个目录，便于整体备份。

## D2：制表符分隔，而不是 JSON 或逗号

格式是每行 `标题<TAB>URL`。关键原因是 **URL 里可以含逗号**（查询串、路径都可能有），
用逗号分隔会把一条书签拆成两条 —— 测试里专门有一条 `urlContainingCommaSurvives` 覆盖它。
制表符出现在标题里的概率极低，且写入前会被替换成空格。

纯文本还能容忍**脏数据**：解析失败的行直接跳过，不会因为一行损坏就丢掉整个书签文件。

## D3：按 URL 去重，且最近添加的排最前

同一个页面只留一条；重复收藏同一个 URL 等于「更新标题并置顶」。
不做「同 URL 多条」，因为那对用户没有意义，只会让列表变脏。

## D4：UI 形态——一个按钮 + 弹出菜单

工具窗横向空间已经很紧（工具栏已经有 5 个按钮 + 地址栏），因此**不做常在的书签列表**，
而是导航行加一个书签按钮，点开是弹出菜单：

```text
☆ 收藏当前页面 / ★ 取消收藏当前页面     ← 依据当前 URL 是否已收藏
──────────────
▸ 书签标题…                             ← 每项一个子菜单
    在当前标签页打开
    在新标签页打开
    ──────
    重命名…
    删除
（暂无书签）                             ← 空态提示
```

设计取舍：

- **每次打开都重新读盘**，不缓存：用户可能直接用编辑器改了书签文件，缓存会看不到改动。
- 书签标题在菜单里按 36 字符截断（超过会把菜单撑得比工具窗还宽），**完整 URL 放在 tooltip**。
- 「在新标签页打开」**复用** `GmHost.openTab`（ADR-0012 为 `GM_openInTab` 建的那条能力），
  没有再写一份建标签页的逻辑。
- 收藏/删除后用状态栏给一句反馈（沿用 `lastError` + `renderStatus()` 的既有做法）。

## D5：默认标题取域名，而不是页面标题

最初用 `document.title` 作为默认标题，实测不可用：**换皮脚本会改写 `document.title` 做伪装**，
默认名于是变成「topic_cache.rs — platform」这类看不出所以然的东西，用户还得手工改。

改为**只取域名**（去掉 `www.`）；域名解析不出来时回落成完整 URL —— 宁可难看，也不要空标题。
代价是**同一站点的多条书签默认名相同**：用每项 tooltip 里的完整 URL 区分，或直接重命名。

## D6：重命名保持原有顺序

重命名**不把条目顶到最前**。重命名是「改个名字」，不是「重新收藏」；若它同时改变排序，
用户会以为书签丢了。名称留空时回落成 URL（与 [BookmarkStore.withAdded] 的规则一致）。

## D7：「在当前标签页打开」必须走 `navigateTo`（实测 bug）

**症状**：在**新标签页**里点书签的「在当前标签页打开」，完全没反应。

根因不在书签逻辑，而在**内核的就绪时序**：

- 面板内核是**延迟创建**的 —— `createBrowserComponent()` 刻意不调 `setCreateImmediately(true)`，
  要等组件拿到非零尺寸，因此 `browser` 字段在内核就绪前一直为 `null`。
- 原实现是 `browser?.cefBrowser?.loadURL(item.url)`。安全调用链把「内核尚未就绪」**静默吞掉**：
  地址栏不变、状态栏不提示、日志也没有。用户看到的就是点了没反应。
- 对照证据：**同一菜单里的「在新标签页打开」一直是正常的** —— 它走
  `GmHost.openTab` → `newTab` → `navigateTo`，而 `navigateTo` 有未就绪兜底。

修复两处：该菜单项改调 `navigateTo(item.url)`；并给 `navigateTo` 的未就绪分支补上
`retryKernelIfNeeded()`，使其真正推进一次内核创建，而不是只把地址存进 `pendingUrl` 干等。

**顺序是易错点**：必须**先设 `pendingUrl` 再驱动重试**。`ensureKernel()` 同步成功时会立刻消费
`pendingUrl`；顺序反了就会变成「内核建好了、却没有任何待加载地址」。

**通用约定**：任何触碰 `browser` 的导航入口都必须处理「内核未就绪」，与地址栏、刷新按钮、
会话恢复保持一致。这类静默失效**无法被单测发现**（Swing + JCEF，需真实 IDE 环境），
只能靠代码约定 + 人工验证，因此已在 `BrowserPanel` 对应位置留下说明性注释。

## 已知限制

- 没有导入/导出浏览器书签（HTML 格式）。
- 没有文件夹分组。当前就是一条扁平列表，按最近添加排序。
- 同一个域名的多条书签默认同名，需要用户自己重命名来区分（见 D5）。

## 验证

```text
BookmarkStoreTest：往返读写 / URL 含逗号 / 按 URL 去重并置顶 / 空 URL 忽略 /
                  空标题回落 URL / 标题里的制表符被替换 / 删除 / 脏行跳过 / contains 去空白 /
                  重命名保持顺序 / 重命名留空回落 URL / 重命名不存在的 URL 是空操作
```

D7 的修复**没有自动化测试覆盖**：它涉及 Swing 与 JCEF 内核时序，需要真实 IDE 环境，只能手工验证。
回归判据：新标签页里点「在当前标签页打开」应立即导航（地址栏同步更新）。
